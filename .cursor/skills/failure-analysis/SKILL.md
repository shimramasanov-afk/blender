# Failure analysis

## Когда применять

Есть симптом на конкретном эпизоде или стабильно воспроизводимый срыв. Не применять вместо проектирования эксперимента.

## Входные данные

- Запись эпизода или способ воспроизвести.
- Конфигурация.
- Версия модели/контроллера.
- Описание симптома (что ожидали / что увидели).
- Если записи нет — сначала воспроизвести на стенде, не гадать.

## Порядок работы

1. Воспроизвести сбой.
2. Найти первый момент расхождения с ожидаемым поведением.
3. Проверить свежесть и качество наблюдений (timestamp, stale, чёрный кадр, HUD).
4. Проверить признаки и их уверенность.
5. Проверить внутреннее состояние (память, сторона обхода).
6. Проверить намерение.
7. Проверить отправленный ввод (на стенде — команду среды).
8. Проверить эффект в среде (позa, столкновение, цель).
9. Определить наиболее вероятную причину. Одна главная, остальные — гипотезы.
10. Сделать минимальное исправление.
11. Добавить содержательную регрессионную проверку (сцена, которая ломалась).
12. Повторить затронутые сценарии, не только счастливый путь.

Не лечить любой сбой увеличением сети, случайностью или специальным условием для одной карты.

## Проверки

- Причина привязана к тику/кадру, не к общему «плохому RL».
- Исправление не подмешивает ground truth в политику.
- Регрессия падала бы на старом поведении (кратко объяснить как).
- Нет обещания «больше не застрянет».

## Результат

```text
симптом
первый тик расхождения
причина
доказательства
исправление
регрессия
повторная проверка (какие сцены, исход)
```

## Когда завершено

Есть причина, доказательство, минимальный фикс и повторный прогон затронутых сцен. Если воспроизвести не удалось — это и есть результат, без «скорее всего».
